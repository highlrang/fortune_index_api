# Premium Consulting Thread Policy

## 목적
유료 사용자에게만 제공하는 `연속 상담 스레드` 기능의 제품 기준을 정의한다.

이 문서는 아래 질문에 답하기 위한 기준 문서다.

- 스레드는 어떤 단위로 유지할 것인가
- 언제 기존 스레드를 이어붙이고 언제 새 스레드를 시작할 것인가
- 프론트와 백엔드가 어떤 UX와 규칙을 공유해야 하는가

## 핵심 결정
스레드 유지 기준은 `사용자 전체 기억`이나 `하루 단위 자동 묶기`가 아니라 `사용자가 선택한 연속 상담 스레드`로 한다.

즉, 문맥 유지 범위는 아래처럼 제한한다.

1. 기본값은 항상 `새 상담 시작`
2. 유료 사용자만 `이전 상담 이어서 하기` 가능
3. 사용자가 명시적으로 이어받기를 선택한 경우에만 같은 스레드에 연결
4. 스레드 내부에서만 문맥 유지
5. 사용자 전체 상담을 하나의 장기 메모리로 자동 통합하지 않음

## 이 기준을 선택한 이유

### 1. 문맥 오염 방지
이 서비스의 상담은 종목, 질문 목적, 시점, 시장 상황에 따라 맥락이 크게 바뀐다.

사용자 전체 상담을 하나로 묶으면 다음 문제가 생긴다.

- 다른 종목 상담이 현재 판단에 섞임
- 과거의 질문 목적이 현재 질문을 오염시킴
- 모델이 중요하지 않은 과거 맥락까지 끌고 와 답변 품질이 흔들릴 수 있음

### 2. 사용자 통제감 확보
`이 상담을 이어간다`는 개념은 사용자 입장에서 명확하다.

반면 아래 기준은 설명력이 약하다.

- 사용자 전체 기억: 왜 예전 상담까지 계속 참고하는지 불분명
- 하루 단위 기억: 왜 날짜가 경계인지 직관이 약함

### 3. 비용과 운영 복잡도 통제
연속 상담을 스레드 단위로 제한하면 토큰 사용량, 보관 범위, 삭제 정책을 통제하기 쉽다.

### 4. 유료 기능으로서의 설득력
`지난 상담을 기억하고 이어서 해석해 주는 기능`은 무료 단발 상담보다 분명한 차별점이 된다.

## 검토한 대안과 결론

### 대안 A. 사용자 전체 상담을 항상 기억
장점:

- 개인화 강함
- 장기적으로 깊은 맥락 구축 가능

단점:

- 문맥 오염 가능성이 큼
- 비용 증가 폭이 큼
- 개인정보 보관 범위가 넓어짐
- 사용자가 원하지 않는 과거 상담까지 반영될 수 있음

결론:
MVP에는 부적합

### 대안 B. 하루 단위로 자동 유지
장점:

- 구현이 단순함
- 자동 정책으로 운영 가능

단점:

- 사용자에게 왜 하루 단위인지 설명력이 약함
- 같은 날 다른 종목 상담이 섞일 수 있음
- 날짜가 바뀌면 자연스럽게 끊긴다는 보장도 없음

결론:
보조 기준으로는 가능하지만 핵심 기준으로는 부적합

### 대안 C. 명시적 연속 상담 스레드
장점:

- 문맥 범위가 명확함
- 사용자 통제감이 높음
- 프리미엄 기능으로 설명하기 쉬움
- 비용과 개인정보 범위 통제가 쉬움

단점:

- 프론트 UX 설계 필요
- 스레드 목록과 상태 관리가 필요

결론:
권장안

## MVP 정책

### 기본 원칙
1. 기본 상담은 항상 `새 상담`
2. 유료 사용자만 같은 흐름을 이어가는 `연속 상담 스레드` 사용 가능
3. 스레드 내부에서만 이전 질문과 답변을 문맥으로 활용
4. 장기 메모리 기능은 MVP 범위에서 제외

### 스레드 생성 규칙
새 스레드는 아래 경우 생성한다.

1. 사용자가 `새 상담 시작` 선택
2. 기존 스레드 없이 처음 연속 상담을 시작
3. 기존 스레드가 만료되었거나 종료됨
4. 사용자가 다른 주제로 분리하고 싶다고 선택

### 스레드 이어받기 규칙
기존 스레드는 아래 경우에만 이어받을 수 있다.

1. 사용자가 명시적으로 `이전 상담 이어서 하기` 선택
2. 해당 스레드가 본인 소유
3. 해당 스레드 상태가 `OPEN`
4. 스레드 만료 시간이 지나지 않음

### 새 스레드를 권장하는 경우
강제는 아니지만 새 스레드를 권장한다.

1. 종목이 바뀐 경우
2. 질문 목적이 크게 바뀐 경우
3. 마지막 상담 후 시간이 많이 지난 경우

질문 목적 변화 예시:

- 매수 타이밍 상담 -> 손절 여부 상담
- 당일 대응 질문 -> 회고/복기 질문
- 특정 종목 상담 -> 전혀 다른 종목 상담

### 스레드 강제 분리 기준
아래 경우는 이어받기를 허용하지 않는다.

1. 스레드 상태가 `CLOSED`
2. 스레드 상태가 `EXPIRED`
3. 사용자 본인 스레드가 아님
4. 유료 사용자 entitlement가 없음

## 시간 기준 권장안

### MVP 기준
- 최근 활동 후 `24시간` 이내: 이어받기 허용
- 최근 활동 후 `7일` 경과: 스레드 `EXPIRED`

### 의미
- 24시간은 "아직 같은 흐름으로 보는 것이 자연스러운 기간"으로 사용
- 7일은 운영상 보관은 하되 활성 문맥으로는 보기 어려운 시점으로 사용

## 프론트 공통 문구 가이드

### 기능 설명 문구
- `연속 상담은 이전 상담 흐름을 이어서 질문할 때 사용합니다.`
- `종목이나 고민 주제가 바뀌면 새 상담이 더 정확할 수 있습니다.`

### 버튼/CTA 문구
- `새 상담 시작`
- `이전 상담 이어서 하기`
- `이 상담 이어서 질문하기`
- `새 주제로 다시 상담받기`

## 백엔드 공통 규칙

### 권장 정책
1. OpenAI conversation 상태와 서비스 자체 스레드 상태를 분리해 관리
2. 서비스의 진짜 기준은 자체 DB 스레드
3. OpenAI conversation은 모델 문맥 저장소로만 사용
4. 상담 결과 요약과 메타데이터는 반드시 자체 DB에도 저장

## 향후 확장 방향
MVP 이후 아래 확장을 검토할 수 있다.

1. 사용자 프로필 요약 저장
2. 종목별 대표 스레드 추천
3. 유사 질문 자동 추천
4. 오래된 스레드 요약 압축 후 새 스레드로 이관

## 최종 권장안 요약
유료 기능은 `사용자가 선택한 연속 상담 스레드`를 기준으로 설계한다.

- 무료: 단발 상담
- 유료: 연속 상담 스레드 생성 및 이어받기
- 기본값: 새 상담
- 문맥 유지 범위: 같은 스레드 내부만
- 이어받기 허용 기준: 사용자의 명시적 선택 + 활성 스레드
- 만료 기준: 24시간 활성, 7일 이후 만료
