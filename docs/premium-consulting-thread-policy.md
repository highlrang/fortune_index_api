# Premium Consulting Thread Policy

## 목적
유료 사용자에게만 제공하는 `연속 상담 스레드` 기능의 제품 기준을 정의한다.

이번 개정에서는 아래 질문에 답하는 기준을 추가한다.

- 스레드는 어떤 단위로 유지할 것인가
- 언제 기존 스레드를 이어붙이고 언제 새 스레드를 시작할 것인가
- 최신 뉴스, 최신 시세, 최신 평균단가를 어떻게 강제할 것인가
- stale 데이터가 섞인 답변을 어떻게 차단할 것인가

## 핵심 결정

### 1. 스레드 유지 기준
스레드 유지 기준은 `사용자가 선택한 연속 상담 스레드`로 한다.

즉, 문맥 유지 범위는 아래처럼 제한한다.

1. 기본값은 항상 `새 상담 시작`
2. 유료 사용자만 `이전 상담 이어서 하기` 가능
3. 사용자가 명시적으로 이어받기를 선택한 경우에만 같은 스레드에 연결
4. 스레드 내부에서만 문맥 유지
5. 사용자 전체 상담을 하나의 장기 메모리로 자동 통합하지 않음

### 2. 모델 선택 기준
메인 모델은 `Gemini`를 사용하되, 스레드 상태는 모델 벤더가 아니라 `서비스 DB`에서 관리한다.

추가로 질의 처리 구조는 아래처럼 2단계로 나눈다.

1. `Router / Intent & Entity Extractor`
2. `Final Response Generator`

Router는 투자 상담 질문 안에서 KIS가 필요한지, 웹검색이 필요한지, 포지션 재조회가 필요한지 판단한다.

Final Generator는 Router가 확정한 최신 데이터만 받아 최종 답변을 만든다.

### 3. 최신성 기준
투자 상담의 정량 데이터와 최신 외부 근거는 아래 원천만 진실로 인정한다.

1. 가격/거래량/밸류에이션: `KIS`
2. 평균단가/수량/손익: `내부 DB`
3. 최신 뉴스/동향: `실시간 웹검색 grounding`

이전 대화에 남은 텍스트 숫자나 모델 기억은 진실 원천으로 사용하지 않는다.

## 이 기준을 선택한 이유

### 1. 문맥 오염 방지
이 서비스의 상담은 종목, 질문 목적, 시점, 시장 상황에 따라 맥락이 크게 바뀐다.

사용자 전체 상담을 하나로 묶으면 다음 문제가 생긴다.

- 다른 종목 상담이 현재 판단에 섞임
- 과거의 질문 목적이 현재 질문을 오염시킴
- 오래된 평균단가나 오래된 시장 상태가 재사용될 수 있음

### 2. 사용자 통제감 확보
`이 상담을 이어간다`는 개념은 사용자 입장에서 명확하다.

반면 아래 기준은 설명력이 약하다.

- 사용자 전체 기억
- 하루 단위 기억
- 벤더 내부 스레드 자동 유지

### 3. 비용과 운영 복잡도 통제
연속 상담을 스레드 단위로 제한하고 메모리로 압축하면 토큰 사용량을 통제할 수 있다.

### 4. 데이터 정확도 확보
투자 상담은 최신성이 중요하다.

아래 방식은 허용하지 않는다.

- 이전 답변에 나온 가격 재사용
- 이전 질문에 적힌 평균단가 재사용
- 며칠 전 뉴스 기억만으로 현재 상황 추정

## 검토한 대안과 결론

### 대안 A. 사용자 전체 상담을 항상 기억
장점:

- 개인화 강함
- 장기 맥락 축적 가능

단점:

- 문맥 오염 가능성이 큼
- stale 데이터가 섞이기 쉬움
- 비용 증가 폭이 큼

결론:
부적합

### 대안 B. OpenAI 서버 측 스레드 중심 설계
장점:

- 대화 상태 관리가 편함
- 구현 속도가 빠를 수 있음

단점:

- 벤더 종속성이 커짐
- Gemini 중심 검색 grounding 전략과 어긋남
- 제품 기준 스레드와 모델 실행 상태가 섞일 수 있음

결론:
보조 수단으로는 가능하지만 기준 설계로 채택하지 않음

### 대안 C. Gemini + 자체 스레드 + 요약 메모리 + 최신 데이터 재조회
장점:

- 모델 선호와 제품 데이터 기준을 모두 만족
- 최신성 정책을 서버가 강제할 수 있음
- 벤더 전환이 쉬움
- 비용 통제가 가능함

단점:

- 메모리/요약 설계 필요
- freshness gate 구현 필요

결론:
권장안

## MVP 정책

### 기본 원칙
1. 기본 상담은 항상 `새 상담`
2. 유료 사용자만 같은 흐름을 이어가는 `연속 상담 스레드` 사용 가능
3. 스레드 내부에서만 이전 질문과 답변의 의미를 문맥으로 활용
4. 장기 메모리 기능은 MVP 범위에서 제외
5. 정량 데이터는 매 요청마다 다시 조회
6. 최신 이슈형 질문은 반드시 웹검색 grounding 사용
7. 라우팅 판단과 최종 답변 생성을 분리한다

### 스레드 생성 규칙
새 스레드는 아래 경우 생성한다.

1. 사용자가 `새 상담 시작` 선택
2. 기존 스레드 없이 처음 연속 상담을 시작
3. 기존 스레드가 만료되었거나 종료됨
4. 사용자가 다른 주제로 분리하고 싶다고 선택

### 스레드 이어받기 규칙
기존 스레드는 아래 경우에만 이어받을 수 있다.

1. 사용자가 명시적으로 `이전 상담 이어서 하기` 선택
2. 해당 스레드가 본인 소유
3. 해당 스레드 상태가 `OPEN`
4. 스레드 만료 시간이 지나지 않음

### 새 스레드를 권장하는 경우
강제는 아니지만 새 스레드를 권장한다.

1. 종목이 바뀐 경우
2. 질문 목적이 크게 바뀐 경우
3. 마지막 상담 후 시간이 많이 지난 경우

질문 목적 변화 예시:

- 매수 타이밍 상담 -> 손절 여부 상담
- 당일 대응 질문 -> 회고/복기 질문
- 특정 종목 상담 -> 전혀 다른 종목 상담

### 스레드 강제 분리 기준
아래 경우는 이어받기를 허용하지 않는다.

1. 스레드 상태가 `CLOSED`
2. 스레드 상태가 `EXPIRED`
3. 사용자 본인 스레드가 아님
4. 유료 사용자 entitlement가 없음

## 시간 기준 권장안

### 스레드 시간 기준
- 최근 활동 후 `24시간` 이내: 이어받기 허용
- 최근 활동 후 `7일` 경과: 스레드 `EXPIRED`

### 데이터 freshness 기준
- KIS 시세: 요청 시각 기준 `5분` 이내
- 포지션 스냅샷: 요청 시각 기준 `1분` 이내
- 뉴스/웹검색 근거: 요청 시각 기준 `24시간` 이내 핵심 근거 1건 이상

### 질문별 강화 규칙
아래 표현이 포함되면 fresh 뉴스 근거를 강제한다.

- `오늘`
- `최근`
- `왜 떨어져`
- `이슈`
- `뉴스`
- `공시`
- `실적`

## 프롬프트/메모리 정책

### 허용되는 문맥
1. 최근 대화 3~6턴
2. 스레드 요약 메모리
3. 사용자 투자 성향
4. 최신 포지션 스냅샷
5. 최신 KIS 시세
6. 최신 웹검색 요약
7. Router가 반환한 정형 라우팅 결과

### 금지되는 문맥 사용
1. 전체 스레드 원문을 매번 전송
2. 과거 평균단가를 자연어 메모리에서 재사용
3. 이전 뉴스 요약을 최신 뉴스처럼 재사용
4. fallback 시세로 매수/매도 결론 단정
5. Final Generator가 스스로 KIS 필요 여부를 다시 추측

### 메모리에 남겨도 되는 정보
1. 사용자가 걱정하는 포인트
2. 선호 리스크 수준
3. 이미 설명한 원칙
4. 다음 턴에서 이어질 질문 맥락

### 메모리에 남기지 않는 정보
1. 현재가
2. 평균단가
3. 평가손익 숫자
4. 오늘 뉴스 제목 목록

이유:
- 이 데이터는 금방 stale 된다.

## 최신성 강제 정책

### 1. 가격 정확도 정책
실시간성 판단이 필요한 답변은 최신 KIS 조회 없이 생성하지 않는다.

금지 예시:
- `지금은 분할매수 기회입니다`를 stale 시세로 단정
- fallback=true인데 실시간 가격처럼 표현

### 2. 뉴스 정확도 정책
최신 뉴스/동향 기반 해석은 grounding metadata와 출처가 있는 경우만 허용한다.

금지 예시:
- 모델 일반 지식만으로 `최근에는 HBM 기대감이 약해졌다` 식으로 단정
- 검색 없이 `오늘 시장은 반도체 전반 악재`라고 말함

### 3. 포지션 정확도 정책
평단/보유수량/수익률 관련 답변은 내부 DB의 최신 조회값이 없으면 제한한다.

금지 예시:
- 이전 턴에서 사용자가 말한 `내 평단 19만 원`을 다음 턴에도 그대로 사용
- 실제 보유 수량 재조회 없이 물타기 판단

## 답변 제한 정책

아래 경우는 일반 투자 판단 답변 대신 제한 응답을 반환한다.

1. KIS 최신 시세 확인 실패
2. 포지션 최신 스냅샷 확인 실패
3. 최신 뉴스가 필요한 질문인데 fresh 뉴스 확보 실패

제한 응답 원칙:

1. 부족한 근거 종류를 명시
2. 단정 표현 금지
3. 재시도 또는 일반론 답변만 허용

예시:

- `최신 시세를 확인하지 못해 지금 비중 확대 여부를 단정할 수 없습니다.`
- `최근 뉴스 근거가 없어 하락 원인 해석은 보류합니다.`
- `평균단가 최신값이 없어 평단 기준 대응은 제시하지 않습니다.`

## Router 정책

### Router가 판단해야 하는 항목
1. `is_investment_query`
2. `requires_market_data`
3. `requires_position_data`
4. `requires_web_search`
5. `symbol`
6. `question_type`

### Router 출력 예시

```json
{
  "is_investment_query": true,
  "requires_market_data": true,
  "requires_position_data": true,
  "requires_web_search": true,
  "symbol": "000660",
  "question_type": "position_decision"
}
```

### Router 운영 원칙
1. 1차는 규칙 기반 분류를 우선한다.
2. 규칙으로 불명확할 때만 소형 LLM Router를 호출한다.
3. Router는 최종 투자 조언을 하지 않는다.
4. Router는 짧은 JSON만 반환한다.
5. 일반 질문 분기는 두지 않고, 투자 상담 질문 안에서 필요한 데이터만 고른다.

## 프론트와 백엔드 공통 규칙

### 공통 정책
1. 기본 선택은 항상 `새 상담`
2. 이어받기는 사용자 명시적 선택일 때만 허용
3. 응답에는 freshness 메타데이터를 포함
4. stale이면 이를 숨기지 않음
5. 출처가 있는 뉴스만 최신 뉴스로 취급

### 프론트 문구 가이드
- `연속 상담은 이전 상담 흐름을 이어서 질문할 때 사용합니다.`
- `종목이나 고민 주제가 바뀌면 새 상담이 더 정확할 수 있습니다.`
- `평균단가와 시세는 상담마다 다시 확인합니다.`
- `최신 뉴스 근거가 부족하면 이슈 기반 판단은 보류됩니다.`

## 운영 감사 정책

### 저장이 필요한 값
1. 답변 생성 시점
2. KIS market as-of
3. 포지션 snapshot as-of
4. 뉴스 검색 as-of
5. grounding citation 목록
6. freshness 판정 결과

### 운영 목적
1. stale 응답 사고 추적
2. 품질 회고
3. 사용자 문의 대응

## 향후 확장 방향

1. 뉴스 출처 신뢰도 계층화
2. 기업 공시/실적 캘린더 전용 연동
3. 포트폴리오 단위 연속 상담
4. 오래된 스레드 자동 요약 재구성

## 최종 권장안 요약
유료 기능은 `사용자가 선택한 연속 상담 스레드`를 기준으로 설계하되, 답변 근거는 매번 새로 조회한다.

- 무료: 단발 상담
- 유료: 연속 상담 스레드 생성 및 이어받기
- 모델: Gemini
- 스레드 상태: 자체 DB
- 문맥 유지 범위: 같은 스레드 내부만
- 정량 데이터 기준: KIS + 내부 DB 최신 조회
- 최신 이슈 기준: 웹검색 grounding
- stale 조건 미충족 시: 투자 단정 답변 제한
