# Home Summary Reviewed Content Schema Proposal

## Goal

Move approved home summary copy from hardcoded runtime rules into reviewed content rows over time, without adding runtime LLM calls.

This is a proposal only. Apply as a DB migration after review.

## Scope

Use this table for reviewed copy generated offline and approved by an operator:

- saju daily stem/branch content
- tarot daily card content
- zodiac moon-sign content
- optional personal template fragments

The home API can keep deterministic fallback logic. DB content should override fallback only when a reviewed active row exists.

## Table

```sql
CREATE TABLE home_summary_interpretations (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    category VARCHAR(30) NOT NULL,
    code VARCHAR(80) NOT NULL,
    variant VARCHAR(80) NOT NULL DEFAULT 'DEFAULT',
    title VARCHAR(120) NOT NULL,
    daily_body TEXT NOT NULL,
    personal_body_template TEXT,
    points_json TEXT NOT NULL,
    active BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

## Constraints And Indexes

```sql
CREATE UNIQUE INDEX uk_home_summary_interpretations_category_code_variant
ON home_summary_interpretations (category, code, variant);

CREATE INDEX idx_home_summary_interpretations_active_lookup
ON home_summary_interpretations (category, code, active);
```

## Category Values

Use stable enum-like values:

```text
SAJU_DAY
TAROT_CARD
ZODIAC_MOON
```

## Code Values

Recommended codes:

```text
SAJU_DAY    -> SajuGanji.code, e.g. MUO, GIMYO
TAROT_CARD  -> TarotCard.code, e.g. FOUR_OF_WANDS, JUSTICE
ZODIAC_MOON -> Korean sign name, e.g. 황소자리, 물병자리
```

## Variant Values

Start simple:

```text
DEFAULT
STABLE
AGGRESSIVE
```

Use `DEFAULT` first. Add risk-profile variants only when the copy materially differs by user risk profile.

## points_json Shape

Store reviewed points as JSON string:

```json
[
  "매수/매도: 신규 진입보다 보유 비중 유지에 집중하세요.",
  "리스크 관리: 리밸런싱은 하되 총 위험 노출은 늘리지 마세요.",
  "마인드셋: 시장이 지루해도 조급함을 줄이세요."
]
```

Application code should parse this as `List<String>` and fall back to deterministic points when parsing fails.

## personal_body_template

Use placeholders only for stable, server-known values.

Supported placeholders proposal:

```text
{userSign}
{userSignKeyword}
{moonSign}
{moonKeyword}
{birthCard}
{birthCardKeyword}
{todayCard}
{todayCardKeyword}
{userGanji}
{userGanjiKeyword}
{todayGanji}
{todayGanjiKeyword}
```

Example:

```text
{userSign} 특유의 {userSignKeyword} 성향으로 새로운 테마에 눈이 가기 쉽습니다. 하지만 {moonSign}의 {moonKeyword} 기운은 실적과 기반을 먼저 보라고 말합니다.
```

Do not allow arbitrary expression syntax. Keep replacement to exact placeholder substitution.

## Runtime Lookup Proposal

Lookup order:

1. Exact `category + code + user risk variant`
2. `category + code + DEFAULT`
3. Deterministic fallback in `HomeService`

Failures should not break the home API:

- missing row -> fallback
- inactive row -> fallback
- invalid `points_json` -> fallback points
- unknown placeholder -> leave unchanged or fallback to deterministic personal body

## Admin API Proposal

Suggested endpoints:

```text
GET    /api/admin/home-summary-interpretations
GET    /api/admin/home-summary-interpretations/{id}
POST   /api/admin/home-summary-interpretations
PUT    /api/admin/home-summary-interpretations/{id}
PATCH  /api/admin/home-summary-interpretations/{id}/active
```

Minimum fields:

```json
{
  "category": "ZODIAC_MOON",
  "code": "황소자리",
  "variant": "DEFAULT",
  "title": "황소자리 달 - 안정과 실물 가치",
  "dailyBody": "...",
  "personalBodyTemplate": "...",
  "points": ["...", "...", "..."],
  "active": true
}
```

Validation:

- `points` must contain exactly 3 items.
- `points[0]` should start with `매수/매도:`.
- `points[1]` should start with `리스크 관리:`.
- `points[2]` should start with `마인드셋:`.
- `dailyBody` should be less than 350 Korean characters.
- `personalBodyTemplate` should be less than 350 Korean characters.
- reject unsupported category values.

## Rollout Plan

1. Keep current deterministic API behavior.
2. Add table migration after review.
3. Add repository/service with fallback behavior.
4. Add admin CRUD only if operators need UI-driven editing.
5. Migrate one category first, preferably `ZODIAC_MOON`, because it has only 12 rows.
6. After QA, migrate `TAROT_CARD`.
7. Keep `SAJU_DAY` on existing `saju_interpretations` unless product wants one unified home-summary content table.

Current seed files:


Apply these files after creating `home_summary_interpretations`:

```bash
mysql -h <host> -u <user> -p <database> < docs/sql/home-summary-saju-day-seed.sql
mysql -h <host> -u <user> -p <database> < docs/sql/home-summary-tarot-card-seed.sql
mysql -h <host> -u <user> -p <database> < docs/sql/home-summary-zodiac-moon-seed.sql
```

For local H2/MySQL-mode development, paste the SQL into the H2 console after the table exists.

Execution prerequisites:

- Run the app's saju interpretation seeding before `home-summary-saju-day-seed.sql`, so `saju_interpretations` has `DAY_PILLAR` rows.
- Run tarot deck seeding before `home-summary-tarot-card-seed.sql`, so `tarot_cards` and `tarot_deck_versions` have active main deck rows.
